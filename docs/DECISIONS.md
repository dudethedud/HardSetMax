# Decisions

| Date | Decision | Why |
|---|---|---|
| 2026-11-08 | The VIP/Crown bot was deleted and replaced with a colour menu bot. All old code, docs and prompts were removed, and a migration drops every old table | Owner: "delete everything, we are making this bot simply for colour role menus". The old code stays in Git history |
| 2026-11-08 | Reppers are recognised by **unlock roles** that other bots already give (server tag, `.gg/femboii` in status); any one of them unlocks colours | Owner: tagging/status is "already handled by other bots to equip a role" |
| 2026-11-08 | Colours are existing roles; the bot never creates or edits roles | Owner picked "your existing roles" |
| 2026-11-08 | One colour across all menus: picking replaces any other menu colour | Owner's choice |
| 2026-11-08 | Layout copies the owner's example: banner, then a box with emoji + underlined heading, role mentions, "Max Selection: 1", and a "Make a selection" dropdown (components v2) | Owner's screenshot |
| 2026-11-08 | Colours come off when the last unlock role goes (member update), plus a sweep at startup and hourly. With no unlock roles configured, nobody is stripped | Events can be missed while offline; an empty config is a setup gap, not people who stopped repping |
| 2026-11-08 | Roles with moderator/admin permissions, bot-managed roles and roles above the bot can't be colours | A menu would hand those to anyone |
| 2026-11-08 | Banners are stored in the database, not as links | Discord attachment links expire |
| 2026-11-08 | Who wears which colour isn't stored; Discord's roles are the record | Nothing to drift out of sync |
| 2026-11-09 | Build on GitHub, not on the host: `.github/workflows/deploy.yml` tests and bundles the bot into one file (esbuild) and force-pushes it with the migration files to a `deploy` branch; Wispbyte runs the `deploy` branch with no `npm install` or build | Wispbyte's free plan blocked the server for "using too much CPU" during `npm install` and the TypeScript build |
| 2026-11-09 | The bot applies migrations itself (`src/db/migrate.ts`): Prisma's advisory lock, its `_prisma_migrations` table and sha256 checksums, one transaction per migration, a failed one blocks startup. Checked: Prisma reports the result as up to date with no drift | The Prisma CLI (~150 MB of packages) can't be on the server without `npm install` |
| 2026-11-10 | Members get a DM when the bot removes their colour for not repping (colour, reason, where to pick again). Closed DMs are skipped; sweep DMs are 3 s apart | Owner request |
| 2026-11-11 | Donations via Ko-fi's webhook (owner picked automatic over staff-confirmed): the bot never handles payments; a per-member code in the Ko-fi message links a donation to a Discord account; private donations stay anonymous; donor emails and messages are never stored; rounds via reset keep history; USD; fund "Giveaway fund" with no goal by default | Owner request; PayPal didn't suit them |
| 2026-11-11 | The bot listens on one HTTP port (`POST /kofi`, `GET /` health) only when the Ko-fi token is set; plain HTTP on the host's port, with a relay as the fallback if Ko-fi requires HTTPS | Wispbyte gives the server one public port; Ko-fi's docs couldn't be checked from the build environment |
| 2026-11-12 | Donor perks: the base Donor role plus tier roles set by `/donations tier`, by lifetime total; members wear only their highest tier. No donor-only colours (colours stay for reppers) and no extra giveaway entries for donors (paid chances to win count as a lottery in many places) | Owner request; owner kept colours separate |
| 2026-11-22 | Christmas invite event (SPEC §8): starts when first deployed with `LEADERBOARD_CHANNEL_ID` and `LEVEL3_ROLE_ID` set, ends Dec 25 12:00 Edmonton; valid = account 30+ days old, stays 7 days, has the level 3 role, never in the server before; members are never DMed | Owner's spec; owner kept the level 3 rule ("Approved") so quick throwaway joins don't count |
| 2026-11-22 | `/invites`, `/leaderboard` and `/invite-link` are public and `/invite-event` is Manage Server: an exception to "commands are admin-only" (CLAUDE.md updated). Levels `everyone` and `manage-server` added to `core/access.ts` | Owner: "Yes, update the rule" |
| 2026-11-22 | New joins stop counting at the end, but joins before it keep being checked until their 7 days are up (about Jan 1). The end post says "final after Jan 1" and the final leaderboard follows a week later; statuses stop changing after it | Owner picked "Keep checking after end"; a last-day invite should get the same chance |
| 2026-11-22 | Personal invite links (`/invite-link`): a permanent invite saved as the member's, credited to them even though the bot created it | Owner asked for it; it's the one join source that can't be confused with another invite |
| 2026-11-22 | Joins are never guessed: two invites up at once, or one up by two, is "unknown" and credits nobody. Nothing up = "discovery" in a discoverable server, else "unknown" (Discord doesn't say which) | Owner's spec: ambiguous joins become unknown |
| 2026-11-22 | Rule 4 ("never joined before") uses everyone present the first time the event runs plus every join since (`KnownMember`). People who left before that look new | Discord has no join history; the bot can only know who it has seen |
| 2026-11-22 | Without Manage Server, invite tracking is off loudly (error log and a staff-log post, re-checked hourly) instead of stopping the bot; colours and donations keep working | Owner: "Disable event loudly" |
| 2026-11-22 | Event times use a fixed UTC-6 for Edmonton, not the host's time zone data | Alberta is on UTC-6 all year from 2026 (tz 2026e); a host with older data would put the end and the Sunday posts an hour off |
| 2026-11-22 | Alt flags go to staff only and never change a status by themselves; staff decide with `review`, `set-status` and `disqualify` | Flags are hints (siblings share names, new accounts are real people) |
| 2026-11-22 | The Sunday 6 PM weekly posts are replaced by one live leaderboard message: posted when the bot starts, edited when it changes, reposted if deleted; the end and final results update the same message | Owner: "post it immediately on bot start and dont repost it just update the same embed"; owner dropped the weekly posts |
| 2026-11-22 | No 7-day wait: an invite counts as **invited** on join and **verified** (a raffle entry) the moment they have level 3; leaving before the end moves it to **left**. The leaderboard ranks like a football table: verified, then invited, then fewer left (left never takes points away), then whoever got there first. Only verified invites are raffle entries. After the end, invited people get 7 days to reach level 3 before the final results | Owner: "make it count immediately … kinda like a soccer leaderboard points then goal difference"; owner picked "left shown only", "verified only" raffle and "7 days to reach level 3" |
| 2026-11-22 | Bots never count as inviters: a join through a bot's invite (e.g. DISBOARD's server listing) is labelled `bot` and credits nobody; joins already credited to a bot are relabelled by the hourly check and hidden from the leaderboard at once | DISBOARD showed up first on the live leaderboard; owner: "ignore bots" |
| 2026-11-22 | The live leaderboard is a components box like the server's message leaderboard: heading, divider, `<badge> @user - **X** verified · …`, small footer. Place badges use the server's `first`…`tenth` emojis, falling back to medals and number keycaps. The old embed message is replaced once, since a message can't be edited into the new layout | Owner's screenshot: "make it look somewhat like this" |
| 2026-11-22 | Place badge emojis are named `first`…`tenth` (one list in `core/emojiText.ts`, used by the donation panel and the invite leaderboard) | Owner renamed the server's emojis |
